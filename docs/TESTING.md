# 測試與部署驗收

## 自動化檢查

```sh
npm ci
npm run check
npm test
```

測試範圍以實際輸出為準。伺服器測試使用模擬 WebSocket peer、HTTP request 及資料庫／翻譯回應；前端以 DOM、模擬媒體與登入回應驗證生命週期。這些測試不等於真實 Supabase PostgreSQL、真實手機瀏覽器或跨國 WebRTC 實測。

本輪應覆蓋已確認帳號與允許名單、房間成員檢查、未授權 API／WebSocket 拒絕、資料庫錯誤不假報成功、離線訊息寫入、相同 ID 去重、分頁，以及登入恢復和重送狀態。通話回歸包含 callId／角色、過期回呼、字幕分離、翻譯失敗不中斷媒體、TURN 權限、十種語言及品質降載。

先前雲端 Chromium 啟動曾回報 `setsockopt: Operation not permitted`。沒有成功的瀏覽器測試證據前，瀏覽器端到端、iPhone Safari、Android Chrome 都必須標為待實測。

## 部署版本核對

先依 [PERSISTENT_CHAT_SETUP.md](PERSISTENT_CHAT_SETUP.md) 建立專案、執行 SQL、建立兩個已確認帳號與設定環境。使用者尚未完成這些設定前，不能宣稱現有網站已具備永久紀錄。

1. 依工作流程先在 LAB 測試，保留公開入口及私房驗證；不要自動更新舊測試站或 NAS。
2. LAB Worker 與此 Node.js／WebSocket 服務協定不同，需要相容整合或獨立測試服務；不能直接替換腳本並宣稱可用。
3. Node.js 20 以上；建置 `npm ci`，啟動 `npm start`，HTTPS 與 WebSocket 需可連線。
4. `/api/health` 應回報此次部署 commit、`protocolVersion: 3`、`storage: "postgres"` 及安全的 `storageStatus`。`configured` 只代表設定完整，不能單獨證明資料庫寫入成功。
5. 未設定資料庫時應明確回報設定不足；不能退回記憶體或檔案並顯示「已保存」。
6. 部署通話協定修改後，雙方都重新整理／重開主畫面 App，避免新舊前端混用。

需要分別記錄 GitHub SHA、實際部署 SHA、資料庫遷移執行狀態與測試日期。不可只用首頁 HTTP 200 推論所有功能正常。

## 持久化與權限：真實 A／B／C 驗收（尚待執行）

使用獨立測試房間。A／B 為兩位允許的已確認使用者；C 為未登入裝置或第三個未列入允許名單的帳號。記錄測試訊息 ID、時間及步驟結果，不記錄私人密碼、token 或服務金鑰。

1. **傳送與確認**：A、B 分別登入同一房間。A 傳送可辨識的測試訊息，確認 B 看見、A 收到伺服器保存確認，資料庫有且只有一列，包含原文、發送者、時間、ID。
2. **雙方關閉再開啟**：完全關閉 A、B 的網頁／主畫面 App，再重新開啟。登入先經驗證，恢復正確語言、愛心及有權限的上次房間，載入剛才訊息，不把自己的訊息誤認為對方。
3. **離線訊息**：A 關閉網站；B 傳訊息並取得保存確認。A 重新登入後能讀到離線訊息，無須 B 再次發送。
4. **斷線與重試**：B 暫時關閉網路後傳訊息，應顯示等待／失敗狀態。恢復網路後以同一 ID 重試；確認沒有重複泡泡或重複資料列。若資料庫寫入失敗，不能顯示已成功保存。
5. **重啟伺服器**：記錄一筆已確認訊息，重新啟動 Node 服務。A、B 重連後仍能從 PostgreSQL 讀取相同 ID 與內容。
6. **Render 重部署**：部署同一已核准版本或無關的小版本更新。驗證程序／暫存磁碟被替換後，歷史仍可載入。此步驟與本機模擬重啟不同，需保留真實結果。
7. **第三人拒絕**：C 即使知道房間碼或 room UUID，也不能透過 `/api/rooms`、`/api/messages`、WebSocket 讀寫訊息或取得 TURN 房間憑證。沒有 Bearer token、過期 token、第三人 token 都應拒絕。直接以 anon key 查私人表格／呼叫專用 RPC 也必須被拒絕。
8. **分頁與順序**：建立超過一頁訊息，載入較舊紀錄。確認穩定排序、無重複、無跳過；包含相近或相同時間的不同 ID。重新載入不應發出訊息通知或重送舊訊息。
9. **清除裝置資料**：清除測試裝置的網站資料，再登入。工作階段和偏好可能需要重設，但 PostgreSQL 的歷史不能因此刪除。登出／登入另一個帳號不能顯示前一帳號的本機暫存。
10. **允許名單與過期**：未確認 Email、被移出允許名單及過期工作階段不得繼續讀寫。測試帳號撤銷後重新驗證；不要以選擇另一顆愛心繞過。

目前以上真實雲端驗收均不得標為成功。完成後請逐項填寫實際結果，將未執行與失敗清楚分開。

## 雙人通話回歸（尚待執行）

1. 兩人分別使用 Wi-Fi 與行動網路；先測語音撥打、接聽、拒接、掛斷、立即重撥，確認 iOS 麥克風指示燈在結束後消失。
2. 測視訊、切鏡頭、關閉／開啟鏡頭；掛斷後相機釋放。差網路應先降低視訊負載，保留音訊。
3. 雙方輪流開啟語音字幕。中文一方看到對方英文原文及中文翻譯，英文一方看到對方中文原文及英文翻譯；自己的話不應誤入接收方字幕區或變成文字聊天泡泡。
4. 關閉／故障翻譯 API 或讓資料庫請求延遲，通話音訊／視訊仍應持續；文字顯示原文及可重試的錯誤，不能假報保存成功。
5. 切換 Wi-Fi／行動網路，觀察 ICE 重連；未配置 TURN 時明示限制，不能保證跨 NAT 可用。
6. 展開品質診斷，只記錄直接／中繼、RTT、遺失率、抖動、解析度／fps、位元率，不記錄 IP、完整 candidate 或秘密。
7. 分別測 iPhone Safari、加入主畫面的 Web App、Android Chrome、背景切換及鎖屏後恢復。持續語音辨識與背景媒體限制需實測；目前不是可靠的系統背景來電服務。
8. 檢查十種語言、白／黑愛心記憶、聊天搜尋、輸入提示、通知設定、拍照與濾鏡仍可使用；通話只播放彼此原聲，不播放 AI 翻譯語音。

Supabase、LLM、TURN、Render 費用與配額各自獨立。此驗收文件不表示已替使用者建立或付費開通任何服務。
